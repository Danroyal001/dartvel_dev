## Fifteen gaps that most block completeness

Ordered by dependencies unblocked, rather than claimed implementation size. “Verify” is evidence debt, not a claim that the implementation is absent.

1. **Visible first-frame document and takeover parity.** Screen CSS clips the fallback even before Flutter starts. This blocks UI, pages, accessibility, SEO-facing presentation and Studio's shared render-path promise.
2. **`initServerState`.** No implementation found; generated typed server state, no-JavaScript first frame, policy and cache semantics remain missing. Existing page-data resolvers are a different contract.
3. **One compiled-app conformance fixture.** Started: `packages/dartvel_cli/test/web_server_binary_test.dart` now drives headless Chrome on a `dartvel create` app's copied binary: server-rendered page, first frame, the semantics button pressed, a generated-client call to a backend function, the answer read as a screen reader reads it, and the write found after a restart. Its first run found a real bug (model pages broke every backend build). Still to add: models through the generated surface instead of SQL, auth, policies, sync, offline. Reuse it across the following gaps rather than promote unit results.
4. **Complete boot, shutdown and request lifecycle.** Verify server/headless entry, graceful drain, streams and worker shutdown; `DV.Platform.entry`, `args`, `launchedAtLogin` are absent on DVPlatform.
5. **Generated model/policy/storage-neutral integration.** Verify all field kinds and database engines; tenant and sensitive policy enforcement must hold before every consumer can be called complete.
6. **Cross-process model sync and presence.** Verify two real clients, fanout, expiry, reconnection and changed authorization; in-process watcher tests do not prove delivery.
7. **Offline persistence and reconciliation.** Verify offline writes through reload, replay, conflicts and revocation against a running binary; a service-worker request queue is not model conflict resolution.
8. **Durable jobs, scheduling and transactions.** Verify separate workers, restart recovery, retries/dead letters and compensation. These underpin imports, webhooks, embeddings and scheduled publication.
9. **Authentication/session/MFA/account browser journeys.** Verify each advertised provider and recovery path, real redirects, token rotation, revocation and tenant policy.
10. **Platform contracts a browser cannot fulfill.** Native tray, global shortcuts, OS menus/login, path-based dialogs, hardware buses/watchdogs and native printing have no corresponding bindings. Explicit refusal is Partial, not successful device support. Several need a different allowed host/carrier, not another browser shim.
11. **Permission/device/browser matrix.** Verify actual allowed actions as well as denial for camera, microphone, location, sensors, Bluetooth, NFC, contacts, fonts, push, fullscreen and PWA file launch. Registration alone proves none of them.
12. **Studio and generated UI end-to-end.** Verify generic projects, their own URLs, edit/publish/review, forms/tables, real assistive technology and keyboard/selection behavior before and after takeover.
13. **Provider-backed product workflows.** Verify search/semantic indexing, AI budgets/tools, mail/push, checkout/entitlements/tax and media capture with genuine adapters or controlled sandbox services, through the built app.
14. **Production operations and module lifecycle.** Complete/verify telemetry export, release health, SLO incidents, privacy erasure, preview isolation and release drain/rollback. Module Health is missing; module source/trust and carrier coverage are partial.
15. **Tooling reliability and reproducible delivery.** Complete source-glob/build/watch/generation conformance, whole-artifact reproducibility and managed Cloud web-server proof. Lead-reported `dartvel --version | head -1` closes stdout and crashes with a stack trace; retain as an open CLI gap.

## Evidence rules and boundaries

- Spec inventory comes from the 106 labelled feature sections in [`spec-status.json`](../spec-status.json); promises are read from [`NEW_SPEC.md`](../../NEW_SPEC.md). Index labels and explanatory status prose were **not** accepted as evidence of target success.
- Source and test files are inspected at the pinned checkout. A test's existence is distinguished from a fresh execution. Unit/widget/generator tests demonstrate only their asserted slice. A real HTTP handler over fabricated assets is stronger than a pure function test but still does **not** build web-server.
- Verified requires target evidence for the complete applicable promise. A complete supported refusal may count only when the spec defines it as the intended outcome; a browser limitation is not silently reclassified Not applicable.
- “Not established” means no qualifying evidence located in this audit, not a declaration that the code cannot work. No external provider accounts, hardware grants or devices were used. Production fleet usage and drag/drop browser checks are lead-reported context, not fresh runs by this audit.
- Browser capabilities belong to the visitor, not the Linux host. HTTPS, a user gesture, permissions, installed-PWA state, engine and physical devices constrain results. A localhost test cannot certify arbitrary production origins/browsers.

## Every canonical binding operation

Inventory: [`binding_names.dart`](../../packages/dartvel_flutter/lib/src/platform/binding_names.dart). Internal binding spelling is shown verbatim; it is **not** a recommendation to expose bridge calls in application code. Application methods sometimes have different names (for example `location.getCoordinates`, `notifications.sendLocalNotification`) or implement the same feature without a bridge (`associations.opened`, PWA updates, windowing).

Important code distinction: `DVNativeBridge.require` throws a StateError naming an unregistered binding; `invoke` returns null. The generic StateError instructs FFI/JNI registration and does not explain a browser restriction. Capability metadata records richer unavailable reasons, but those sentences are not automatically the error a caller receives. Fonts adds a reason-bearing result; windowing adds its own degradation codes. An optional-API denial can throw `DVWebPermissionDenied(binding, reason)`; some helpers wrap results differently. Never infer a successful action from being in `dvWebImplementedBindings`.

Missing bindings with native-only contracts are still shown Partial here to expose browser limits, even when the containing native-target feature is Not applicable. Each supported binding below is Partial pending a complete built-app browser success/refusal journey. Each absent binding is Partial because the surrounding platform surface exists but cannot fulfill this native operation in a browser. No fabricated hardware/path/print success is credited. The restriction text was cross-checked against browser registration/helper sources; a name in the unavailable catalogue alone is not proof of a public API failure.

## Docs that overclaim or blur the boundary

These are local source/document mismatches or evidence gaps, not an endorsement of every other paragraph. Designed text explicitly labelled designed is not counted as an overclaim.

- [`NEW_SPEC.md`, Platform](../../NEW_SPEC.md) lists `DV.Platform.entry`, `args`, `launchedAtLogin` and describes currentPlatform as an enum. `DVPlatform` has none of those three entry getters and returns a String for currentPlatform. The section mixes designed entry promises into the existing surface.
- The identical feature table in [`AGENTS.md`](../../AGENTS.md) / [`CLAUDE.md`](../../CLAUDE.md) says every listed feature is “Implemented”, including Platform, sync, notifications and AI. Its later disclaimer correctly calls this intended design, but the table cannot be used to answer feature coverage; browser bindings, generated integration and real target verification remain incomplete.

- README PWA says real Chrome tests run “on every push”. A workflow/test declaration alone is not evidence of a successful run for this checkout. Existing browser evidence also does not certify the entire web-server installed/offline/update journey. README's later explicit first-frame caveat is accurate.
- [`web_capabilities.dart`](../../packages/dartvel_flutter/lib/src/platform/web/web_capabilities.dart) explains missing names as a reason-bearing distinction; `DVNativeBridge.require` actually emits a generic unregistered-binding StateError and `invoke` returns null. Do not promise the capability-map reason at every public call site. This matters especially for hardware, printing and native path dialogs.
- [`file_bindings.dart`](../../packages/dartvel_flutter/lib/src/platform/file_bindings.dart) describes web files as unsupported; [`web_files_js.dart`](../../packages/dartvel_flutter/lib/src/platform/web/web_files_js.dart) now registers real OPFS operations. This is stale underclaim rather than overclaim, included because it would produce the wrong browser gap list.
- `associations.opened` and `window.open/displays` in the core unavailable list are **not** proof of missing whole features: launchQueue and the separate windowing web host implement alternate delivery. Likewise absent `updates.*` native bindings do not mean PWA service-worker updates do not exist.

## Known renderer and CLI gaps

The renderer gap is directly confirmed in [`page_text.dart`](../../packages/dartvel_core/lib/src/web/page_text.dart): `dvFallbackCss` applies a screen rule with fixed position, 1px dimensions, overflow hidden and `clip-path:inset(50%)`; noscript/print rules separately reveal the document. It is present in HTML for crawlers and does not satisfy a visible, selectable app-themed first frame with JavaScript enabled. HTTP text-presence tests cannot detect this visual failure. This audit did not modify it or run a new screenshot comparison.

The closed-pipe `dartvel --version | head -1` crash is reported by the lead's 22 October release handoff. It is recorded as open, **not freshly reproduced** or fixed here. Reproduction must inspect stderr and pipe statuses; an exit code from head alone would hide the producer's crash.
