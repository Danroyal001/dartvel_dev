## 1. Windows — ✅ verified, artifact inspected

This target had never once reached the Dartvel CLI. It now does.

- [x] **The hang.** Not Flutter — the native asset hook. `cargo build` was
      unbounded, so a cold-cache compile of ~200 crates was indistinguishable
      from a wedge, and it ran to whatever cap it was given (257 and 226
      minutes on two earlier attempts). The hook runs before `dart run` reaches
      a `main`, which is why the CLI's `--build-timeout` could never help.
      Bounded and streamed; Rust now compiles in **3m22s**.
- [x] **ffigen could not find the pub cache.** Revealed only once the hang was
      gone. A child process inherited an environment with neither `PUB_CACHE`
      nor `LOCALAPPDATA`. Fixed with `hookChildEnvironment`.
- [x] **Visual Studio detection is a false negative.** Dartvel probes for `cl`
      on `PATH`; `cl` is not on `PATH` outside a Developer Command Prompt, so
      a runner with the full C++ workload installed is reported as missing it
      and the build **skips**. Flutter itself uses `vswhere.exe` at
      `%ProgramFiles(x86)%\Microsoft Visual Studio\Installer\vswhere.exe`.
      Fix it the way the others were fixed: pure function first
      (`visualStudioFoundIn(vswhereOutput)`), then wire a probe onto
      `ToolRequirement`.
- [x] **Four more Windows bugs, found by getting that far and fixed.** `esc`
      never escaped backslashes, so generated code did not compile
      (`7a327722`); a route is a URL and the host separator must not reach it
      (`ff05af0f`); the same doubled-backslash fault was in six more places
      (`201affb5`); glob patterns are not paths, and a root guard had never
      been discovered (`b32e96d1`).
- [x] **Artifact produced and inspected**, run
      [32587129093](https://github.com/Danroyal001/dartvel/actions/runs/32587129093).
      Downloaded and listed rather than inferred from an exit code:
      `dartvel_example.exe` (89 KB, *PE32+ executable (GUI) x86-64, for MS
      Windows*), `dartvel_shelf.dll` (7.2 MB — the Rust runtime compiled for
      Windows), `flutter_windows.dll` (21 MB) and `data/`. Eight attempts,
      seven bugs, four of which were silent corruption on every platform
      rather than Windows quirks.

## 2. macOS — ✅ verified, artifact inspected

- [x] **The hang is gone, and it was never Flutter.** The native asset hook
      buffered its output, so a long C compile was indistinguishable from a
      wedge. Bounding and streaming it turned the hang into a visible failure:
      **cc-rs invoked with no `-isysroot`**, because `SDKROOT` was unset and no
      C crate could find its headers. Removing `aws-lc-rs` first was the useful
      failed fix — `ring` and `zstd-sys` then failed identically, which pointed
      at the environment rather than any dependency. Artifact verified: a
      Mach-O **universal binary** (x86_64 + arm64) with `dartvel_shelf.framework`
      bundled. Superseded detail below, kept only as the record of what it was:
      its native hook finishes in **11.71 seconds**, so it
      is not the Windows bug. `🔨 Building for macos...` prints and then
      nothing for 41 minutes. No `xcodebuild` among the orphaned processes at
      cleanup, only two `dartvm` — so Flutter starts, blocks before printing
      anything, and never reaches Xcode. `_isPlatformAvailable` is pure and
      cannot be it, and both child pipes are drained, so silence means the
      child produced nothing rather than that output was lost.
- [x] The next probe should capture what the process is *doing*, not only that
      it stopped: `sample` or `spindump` on the wedged `dartvm`, uploaded as a
      diagnostics artifact.

**Do not conflate this with Windows.** They looked identical from the outside
and were not the same bug at all; assuming they were is what would waste the
next attempt.

## 4. Terminal rendering — designed, two steps built

Specified today in `NEW_SPEC.md` § Terminal Rendering. `Draft`/`Partial`.

- [x] `-cli` / `-tui` suffix resolution, refusal on platforms with no terminal,
      and `resolveRenderBackends` — the rule that no build links a backend it
      did not ask for. 10 tests.
- [x] Read `dartvel.terminal` from `pubspec.yaml` and feed it to
      `resolveRenderBackends`. Pure Dart, testable now.
- [x] `DV.Platform.surface`, `DV.Platform.terminal` and `.graphics`. Installed
      at startup from what was linked, never probed — probing would make the
      presentation a runtime question, which is what would force every app to
      ship both backends.
- [x] Launch negotiation: GUI by default, `--tui`, the no-display prompt, and
      the non-interactive case where a prompt would be a hang. Returned as an
      outcome rather than performed, so every branch is testable without a TTY.
- [ ] Terminal size as a signal, so a resized terminal drives the same reactive
      path a resized window does. Lands with the backend.
- [ ] **`dartvel_flt` fork** of [`jiahaog/flt`](https://github.com/jiahaog/flt)
      — Rust, Flutter's Custom Embedder API, Kitty graphics with an ANSI
      fallback. Upstream runs apps in development and does not produce
      distributable binaries; supplying that is the fork's job. Do this last —
      it is the part with an engine pin and the most ways to go wrong.

`android-cli` stays out, deliberately. Termux is Android userland: bionic, not
glibc, and no `/lib/ld-linux-aarch64.so.1`, so a `linux-cli` binary does not
fail partway through — it does not start. A test asserts the refusal.

## 5b. The SDK floor is a fiction, and raising it breaks a test — DONE

`dartvel_mix` is forked and pinned to Dart 3.12 / Flutter 3.44, and
`dartvel_flutter` resolves against it. Every other package declared
`sdk: ">=3.4.0 <4.0.0"` while depending on it, so **no 3.4 SDK could ever have
resolved this project** — the number was misleading rather than permissive, and
it was the number the Fuchsia build failure quoted.

- [x] **The vscode test failure was never about the language version.** The
      bisection was sound and its conclusion was wrong. `_isFresh` compared a
      file's mtime against a `DateTime.now()` taken when the build started;
      mtime granularity is a second or worse, `DateTime.now()` is microseconds,
      so an artifact written immediately after the build began could carry a
      timestamp numerically below it and be reported missing. Order-dependent
      because it depends on where in the second the build starts — which is
      exactly what "passes in isolation, fails in a full run" looks like, and
      what made a language-version explanation seem to fit.

      Worth keeping as a lesson: the bisection isolated the file correctly and
      then the *reason* was inferred rather than measured. Ruling out
      dependency resolution left "language version" as the only remaining
      candidate considered, and it was recorded as the cause on that basis.
      Nothing in the vscode path was ever read.

- [x] **All eight pubspecs now declare `>=3.12.0`** — six packages, the root,
      and all three examples — and the consistency test is restored as
      `test/unit/sdk_floor_test.dart`, wired into CI as its own `sdk-floor` job.
      It computes each package's real requirement from the resolved dependency
      graph instead of asserting a version written in the test, so a dependency
      raising its own floor fails it rather than passing unnoticed. It also
      asserts every package agrees on one number; that assertion was watched to
      fail before it was kept.

      One number rather than a per-package floor, deliberately. The backend
      packages genuinely only need 3.9, and writing that down separately is how
      webOS got measured against the wrong floor.

- [x] **`packages/dartvel` was resolving pub's `mix 2.1.0`, not the fork.**
      Found while checking the above. No lockfiles are committed, so a fresh
      clone was unaffected and nothing shipped wrong — but every local test run
      of the umbrella package had been exercising upstream `mix` rather than
      `dartvel_mix`, which is the package the superset claim rests on.

## 5c. Found while fixing 5b — the native library that ships was stale

- [x] **The committed `lib/native/linux-x64/libdartvel_shelf.so` was six days
      old and did not export `dv_http_next_event`.** It therefore predated the
      entire Rust HTTP client. The HTTP/2 work was verified through cargo's own
      test harness against a freshly built crate — which is real verification
      of the Rust — but `DVRustHttpTransport` could not have worked against the
      library that actually ships, and nothing said so.

      The cause is a reasonable design with a missing check: the build hook
      skips when cargo or cbindgen is absent, so an unrelated `dart run` does
      not compile Rust. Nothing then compared the committed binary against the
      generated bindings. `test/native_symbols_test.dart` now does, naming the
      missing symbols and the command that rebuilds them.

- [ ] **The other platforms' committed libraries have not been checked.** The
      symbol test skips when there is no library for the host, so only Linux is
      actually covered by a run here. Whether the macOS and Windows binaries
      are equally stale is unknown, and answering it needs those hosts.

- [x] **Two servers in one process served each other's routes.** The Dart
      request handler was a single global that every `aw_start` overwrote, so
      the last server to start answered for all of them — with a plausible 404
      from the wrong router rather than an error. Now keyed per server.

- [x] **A failed bind reported success.** `aw_start` returned a positive id
      before anything tried to listen; the bind happened later inside a
      detached thread, where its panic was invisible. Now bound on the calling
      thread, with distinct codes for a bad address and a failed bind.

## What changed today, for context

CI now runs the test suites at all — it did not before, so a green commit meant
nothing had been checked. It found a stale `DVStaticPaths` export on its first
run. The spec-status check was path-filtered in a way that could never catch
the thing it exists to catch, and now is not. Diagnostics upload as artifacts
because the Actions logs endpoint throttles reads for long stretches, always
when a failing build most needs reading.

`@DVStaticPaths` was folded into `@DVModel(publicPathsResolver:)`. `computed`
was removed in favour of operating on signals directly. Git history was
rewritten across eight repositories to remove AI attribution, verified
byte-identical.

Two rules were written into the eleven agent files today because they kept
being lost: no AI attribution in commits, and test-driven development —
failing test first, and never adjust a test so existing code passes.
